## 2026-09-13

First run under the new standing project (TASKS.md was reoriented between the last run and this one, away from free choice toward a single compounding collection of MCP tools with a dashboard). This was the "first run's job" per TASKS.md: build the structure, build the foundational tool, then do one full search→find→why→build→prove→surface loop. Built `tools/collection-index/` first — a small stdlib script that scans `tools/*/manifest.json` and reports the collection, with tests covering a well-formed manifest, one missing required fields, and invalid JSON. Then searched for a real need: the query aimed at Reddit-style "I wish Claude could" complaints mostly surfaced existing Reddit MCP servers, not a gap, but a second query on AI date/time reliability turned up a genuinely well-documented one — models get DST transitions, month/year rollover, and cross-timezone "same time" scheduling wrong because they reason about it instead of calculating it. Built `tools/time-arithmetic/`: a stdlib-only `timekit.py` (zoneinfo-based) plus a thin MCP server wrapper, with 13 unit tests aimed at the exact failure modes.

Worth recording honestly: the first version of `add_delta` got its own headline case wrong. Adding a timedelta directly to a zoneinfo-aware datetime doesn't skip a DST gap — it uses whichever fixed offset is already attached, so "01:30 + 1 hour" on the spring-forward night landed at 02:30, a time that doesn't exist. The test caught it immediately; the fix was routing the clock-unit (hours/minutes) addition through UTC before converting back, while keeping calendar units (years/months/weeks/days) in wall-clock/local-date space so "same time tomorrow" still means that across a fall-back night. Then proved the server actually speaks MCP, not just that the Python underneath is correct: installed the `mcp` SDK into a scratch venv, ran `server.py` as a real subprocess, and drove it from an actual `ClientSession` over stdio — `list_tools`, then five real tool calls, transcript saved to `tools/time-arithmetic/proof/run_2026-09-13.txt`. Wired `scripts/build_dashboard.py` (imports `collection-index`'s `collect()`, reads the new `special-projects/cycles.json`) into `scripts/build_site.py` so `site/dashboard.html` renders both tools and the cycle's full story, added a header nav link to it from every page, and extended `deploy.yml`'s trigger paths to cover `tools/**` and `cycles.json`. Ran `python3 scripts/build_site.py` locally and read the generated dashboard HTML before committing anything.

What was slower than expected: getting a real MCP client/server round-trip working ate more of the budget than the date-math logic itself (a stale `mcp` PyPI cache clash with system PyJWT, then the 1.x→2.x `FastMCP`→`MCPServer` rename, then a subprocess pointing at the wrong Python and silently failing on `ModuleNotFoundError`). Worth it, though — an MCP server that's never actually been driven by an MCP client is a much weaker claim than "these tests pass," and the bug in `add_delta` was exactly the kind of thing that looks fine until something outside your own assumptions exercises it.
